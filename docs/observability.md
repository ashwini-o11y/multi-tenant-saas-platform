# M8.1 Observability Foundation

M8.1 adds OpenTelemetry-compatible traces and metrics plus structured request logs to the existing FastAPI API. It does not change tenant authorization, business routes, or persistence. Telemetry is disabled by default, and the application does not require a collector to start or serve requests.

## Observability architecture

The API uses automatic OpenTelemetry FastAPI/ASGI instrumentation for server spans and standard HTTP telemetry. A small ASGI middleware adds service request count and duration measurements and writes one structured JSON-compatible request log. The middleware uses FastAPI's matched route template, not raw URLs, as the route dimension. Trace and metric resources identify the service as `multi-tenant-saas-api`.

The telemetry paths are:

```text
FastAPI request
  ├─ OpenTelemetry FastAPI instrumentation -> server spans + HTTP metrics
  ├─ validated TenantContext -> tenant.id span attribute + request state
  └─ request middleware -> tenant-aware service metrics + structured stdout log
```

## Telemetry types

- **Traces:** automatic server spans with HTTP method, route, response status and service resource attributes.
- **Metrics:** OpenTelemetry HTTP instrumentation plus `saas.http.server.request.count` and `saas.http.server.request.duration`. Attributes include matched route, method, response status, and `tenant.id` only when tenant validation succeeded. These dimensions can support later request-volume, success/failure, latency, and tenant reliability analysis.
- **Logs:** one JSON-compatible request event with UTC timestamp, level, service/version, matched route, method, status, duration, trace/span IDs when available, and validated tenant ID when present.

M8.1 establishes signals only. It does not calculate SLIs/SLOs, error budgets, burn rates, or alerts.

## Configuration

Set these environment variables as needed:

| Variable | Default | Description |
| --- | --- | --- |
| `OTEL_ENABLED` | `false` | Enables SDK providers and OTLP trace/metric exporters only when set to `true`. |
| `OTEL_SERVICE_NAME` | `multi-tenant-saas-api` | OpenTelemetry `service.name`. |
| `APP_VERSION` | `1.0.0` | OpenTelemetry `service.version`; dev deployment supplies its Git SHA. |
| `DEPLOYMENT_ENVIRONMENT` | `local` | OpenTelemetry `deployment.environment.name`. |
| `OTEL_EXPORTER_OTLP_ENDPOINT` | Exporter default | OTLP HTTP endpoint, supplied by the environment; no collector URL is hard-coded. |
| `OTEL_EXPORTER_OTLP_PROTOCOL` | `http/protobuf` | Supported OTLP protocol. Other values fail configuration explicitly. |
| `OTEL_EXPORTER_OTLP_TIMEOUT` | Exporter default | Standard OTLP exporter timeout in milliseconds. |
| `OTEL_RESOURCE_ATTRIBUTES` | none | Additional standard OpenTelemetry resource attributes. Do not put secrets or personal data here. |

The pinned exporter uses OTLP over HTTP/protobuf and honors the standard endpoint and timeout variables, including signal-specific endpoint variables. No credentials or collector endpoint are committed. Supply an endpoint only through runtime configuration.

## Tenant-aware telemetry

The existing `get_tenant_context` dependency remains the only tenant source for telemetry. After the tenant has been loaded and confirmed `ACTIVE`, the dependency stores the canonical tenant ID on request state and adds `tenant.id` to the active server span. Request metrics and logs use that validated state; they do not copy the raw header.

Missing, unknown, suspended, or deactivated tenants do not receive a tenant telemetry attribute. The tenant-independent `/health` endpoint remains independent. Cross-tenant data isolation and the simplified, non-authenticating `X-Tenant-ID` behavior are unchanged.

## Structured logging and correlation

Request logs are emitted to stdout as JSON with a fixed set of fields. The logger records only method, matched route, status, duration, service metadata, trace/span IDs, and validated tenant ID. It does not log raw URLs or query strings, request/response bodies, arbitrary headers, or tenant/customer records. HTTP instrumentation explicitly limits captured request headers and sanitizes `X-Tenant-ID`; validated tenant context is added separately.

Trace and span IDs are taken from the active OpenTelemetry server span (captured when the span is created if request middleware runs after its context exits). IDs are never generated by the logging code. With telemetry disabled, trace/span IDs are `null`.

## Local development and unavailable collectors

By default, `docker compose` sets `OTEL_ENABLED=false`; tests and local API use require no collector. The API continues to serve `/health` when telemetry is disabled.

When explicitly enabled, SDK initialization configures batched trace export and periodic metric export using OTLP environment configuration. Export occurs asynchronously and collector connection failures are handled by the OpenTelemetry exporters; they do not gate request handling or API startup. Configure a short exporter timeout for local smoke tests if a collector is unavailable. The API itself does not fall back to fake successful exports.

For example, an operator may enable the SDK and provide a collector endpoint at runtime:

```bash
OTEL_ENABLED=true \
OTEL_EXPORTER_OTLP_ENDPOINT="<operator-configured-otlp-endpoint>" \
OTEL_EXPORTER_OTLP_PROTOCOL=http/protobuf \
python -m uvicorn app.main:app
```

## Security and privacy

Telemetry intentionally excludes customer names, email addresses, transaction data, request payloads, authorization headers, cookies, and raw query strings. Only validated tenant IDs are exported for tenant-level reliability analysis. Tenant IDs are still identifiers: restrict collector access and retention appropriately. Do not add secrets to resource attributes or exporter configuration.

## M8.1 boundaries and roadmap

M8.1 does not add a collector, Prometheus, Grafana, Jaeger, Tempo, Loki, a log backend, dashboards, SLO calculations, SLIs, error budgets, burn-rate alerts, or paging. Logs go to container stdout and OTLP telemetry is exported only when explicitly enabled.

Later M8 increments can add an operator-managed telemetry backend, define SLIs from request count/status/latency metrics, set service and tenant reliability objectives, calculate error budgets, and introduce alerting. Those capabilities are not claimed by this foundation.
